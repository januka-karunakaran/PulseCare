# MongoDB Index Migration Plan & Production Safeguards

## 1. Overview
Feature 02.1 introduces new collections and indexes to enforce database-level concurrency protection without breaking existing production collections or requiring destructive data migrations.

---

## 2. New Collections & Indexes

### 2.1 Collection: `appointment_slot_reservations`
- **Purpose:** Database-enforced atomic claims on single-capacity doctor appointment slots.
- **Indexes:**
  1. `_id`: Unique primary key index (auto-generated by MongoDB).
     Format: `canonicalDoctorId_appointmentDate_normalizedTime`
     Example: `64a8f9c102b_2026-12-01_10:00 AM`
  2. `slot_reservation_compound_idx`:
     `db.appointment_slot_reservations.createIndex({ "doctorId": 1, "appointmentDate": 1, "appointmentTime": 1 }, { unique: true })`
  3. `appointmentId_idx`:
     `db.appointment_slot_reservations.createIndex({ "appointmentId": 1 })`

### 2.2 Collection: `daily_queue_counters`
- **Purpose:** Monotonic, atomic daily queue token numbers per doctor per day.
- **Indexes:**
  1. `_id`: Unique primary key index.
     Format: `canonicalDoctorId_appointmentDate`
     Example: `64a8f9c102b_2026-12-01`

### 2.3 Collection: `beds`
- **Field Added:** `currentBookingId` (String, nullable).
- **Index:**
  `db.beds.createIndex({ "status": 1 })`

### 2.4 Collection: `bed_bookings`
- **Indexes:**
  `db.bed_bookings.createIndex({ "bedId": 1, "status": 1 })`
  `db.bed_bookings.createIndex({ "patientId": 1 })`

## 3. Legacy Production Data Assessment & Dry-Run Procedure

### Pre-Deployment Verification:
1. **Detect Pre-existing Duplicate Active Appointments:**
```javascript
// Dry-run inspection query for duplicate active slots in existing database
db.appointments.aggregate([
  { $match: { status: { $in: ["PENDING", "CONFIRMED", "APPROVED", "SCHEDULED"] } } },
  { $group: {
      _id: { doctorId: "$doctorId", date: "$appointmentDate", time: "$appointmentTime" },
      count: { $sum: 1 },
      ids: { $push: "$_id" }
  }},
  { $match: { count: { $gt: 1 } } }
]);
```
- If duplicate active appointments exist from previous versions, clinical administrators must review the affected records before populating `appointment_slot_reservations`.
- Historical cancelled (`CANCELLED`), completed (`COMPLETED`), or rejected (`REJECTED`) appointments are **NOT** indexed into `appointment_slot_reservations`, ensuring legacy history is 100% preserved.

2. **Detect Pre-existing Over-allocated Beds:**
```javascript
// Dry-run inspection query for multiple active bookings on the same bed
db.bed_bookings.aggregate([
  { $match: { status: "ACTIVE" } },
  { $group: {
      _id: "$bedId",
      count: { $sum: 1 },
      bookingIds: { $push: "$_id" }
  }},
  { $match: { count: { $gt: 1 } } }
]);
```

## 4. Safe Deployment & Rollback Strategy

### Step-by-Step Deployment:
1. Deploy new backend application code.
2. Spring Data MongoDB automatically creates the `appointment_slot_reservations` and `daily_queue_counters` collections upon first insert.
3. Background index creation (`background: true` in production) ensures zero downtime.
4. Active appointments will register reservations as they are booked or modified.

### Rollback Plan:
If rollback is required:
1. Revert backend application code to previous release commit (`dbdd37b`).
2. The newly introduced collections `appointment_slot_reservations` and `daily_queue_counters` are completely isolated and do not impact legacy collections (`appointments`, `beds`, `bed_bookings`).
3. No data loss occurs for existing appointments or patient profiles.
